# Plan B2: Wave 2 (the 10022 levers first, then the level 5-36 systems)

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax. Save this file as `docs/superpowers/plans/2026-11-25-plan-b2-wave2.md`.

**Goal.** Give a fresh character the original game's tools for chapter-1 boss stage 10022, then build the single-player systems that unlock between player levels 5 and 36. Run 9 (`docs/dev-loop.md` §7, 25-11-2026) showed that 10022 is not lost because of a server bug. Three level-3 one-star heroes are about five times too weak for the wave-3 dragon, and the original's levers for this point do nothing on our server today. Phase A opens with those three levers, in this order:
1. The rest of the gacha: the daily free supreme draw, the post-guide 2-star hero and the hero-guarantee interval.
2. Hero skill upgrade (`5_2103`).
3. Training with xp potions (`5_2139` and the train requests, item 1100).

ACC-W2-1 then proves the path end to end. A fresh character plays the guide, takes the free post-guide draw, levels skills, trains and wins 10022. After that the chapter chest, achievement kind 2 and guide 10400→10420 follow.

Phase B then builds the other Wave 2 systems in parallel: angel spell and aura, elite stages with the elite item sweep, the mystery merchant, the gold trial, hero trials, angel trials and runes. Phase C wires them and adds daily tasks. The client is the spec. Every number below comes from a stock `.db` table or from a Lua line cited next to it.

**Architecture.** It keeps the B1/Wave-1 contract (`handlers(registry, settings, conn, cfg) -> {(svc, cmd): fn}`, `fill_required`, `Session.queue`).
- **Phase A is serial.** It touches shared files (`db.py`, `config/__init__.py`, `gacha.py`, `hero.py`, `level.py`, `bag.py`, `player.py`, `__main__.py`) and ends with A6, which lays all Phase B schema, config lookups and `QueryMyselfRes` fields so that no Phase B task touches those files.
- **Phase B is parallel in worktrees.** Each task owns one module (NEW, or one pre-existing module no other Phase B task touches) plus its tests.
- **Phase C is serial:** wiring, daily tasks (call sites in many files), ACC-W2-2.

**Tech.** `py -3.14`, protobuf 7.36.2, pytest 9, stdlib sqlite3/asyncio, AVD `LOA_API30`. No client (APK) change is needed anywhere in this plan.

**Read first.** `docs/superpowers/plans/2026-11-24-plan-b2-wave1.md` (Global constraints, settled points 1–17, O1–O8), `docs/dev-loop.md` §7 runs 7, 8 and 9 plus the pre-launch checklist, `docs/TODO.md`, `docs/protocol.md`.

## Global constraints (house rules baked in)

- Python is always `py -3.14`. The test command is `py -3.14 -m pytest -q --basetemp=C:/tmp/pytest-loa-<task>`, with a **distinct basetemp per task/worktree** (forward slashes). Never share a basetemp between parallel runs.
- **Never `git push`.** Work on the NEW branch `plan-b2-wave2`, cut from `plan-b2-wave1` at `3b8d44c` (suite `605 passed`). Make one local commit per task, or per numbered sub-commit where a task says so. Messages look like `feat(server): ...` and end with the attribution line from the session reminder.
- Parallel tasks run in git worktrees. `.stock/` and `data/` are gitignored. In each worktree, junction the main tree's `.stock` read-only with `cmd //c mklink /J .stock "<main-tree>\.stock"`. Never copy or modify it. **Never `git stash`** in a worktree, because the stash is shared.
- `data/player.db` migrations are additive only: `CREATE TABLE IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`, and `ADDED_COLUMNS` in `server/db.py`. Never rebuild a table. Every `data/player.db.*` world must still load.
- Status codes are the client's own `language.db` ids, quoted per handler. Never invent one. A non-zero body `status` floats the language text and skips a listener that has no `isRecError` (`MMMsgDispatcher.lua:107-131`).
- **A Res with no `status` field cannot refuse**, because the native header supplies 0 (TODO "Known client behaviour"). In Wave 2 these are `BuyXpItemRes`, `UpgradeAngelSpellRes`, `RuneLevelUpRes`, `UseCleanEliteItemRes`, `HerotrialsInfoRes`, `HerotrialsBattleRes` and `AngeltrialsEndBuyBuffRes`. Such a handler changes nothing on a shortfall, logs WARNING with the language code it would have used, and answers the current state.
- Every response and every queued notify goes through `fill_required`.
- Config reads go only through `server/config/`. Stock `.db` TEXT columns get a cast.
- Writes: validate the whole cost and the whole prize list first, then write. This is the same pattern as `item.grant_prizes`.
- Hero fields on the wire are **hero entries** (Wave 1 rule 28). Angel fields are **angel entries**.
- Dates a human reads (log lines, doc tables) are `dd-mm-yyyy`. Stored values are ISO `YYYY-MM-DD` or epoch seconds. **Flatpickr and the responsive recipe: N/A** (no web UI in this plan).
- Do not add an abstraction with one caller. This plan adds three helpers that do have two or more callers: `db.day_key` (gacha, angel trials, daily tasks), `db.add_angel_xp` (moved out of `level.py`; level and train) and `cfg.function_unlock` (skill, train, trials, merchant).

## Assumptions and open questions

**Settled by reading the client (not open):**

1. **The free supreme draw rides the normal request.** When `freetimes > 0` the client still sends `5_2123 {gacha = 2400000}`. It only decrements its own copy and marks the draw free (`TavernFace.lua:171-191`, then `:238-253`). Today the server answers `5_2121` with `freetimes = gacha_info.free_times` (1) and `cooldown = 0` forever (`gacha.py:58-63`), so the client shows "free" every time while the server charges 2,000 diamonds (run 9 row "Free diamond draw"). The client's rule is "the first draw after 05:00 each day is free" (`z00512 = "每日5:00后首抽免费"`, `Language_cn.lua:696`; `TavernFace.lua:68-75`). `cooldown` drives nothing: every branch that reads it has its body commented out (`TavernUtil.lua:198-207`; TavernCD's countdown is commented out, `TavernCD.lua:44-64`).
2. **A paid supreme single needs ticket 99, not diamonds.** For the supreme card (`idx 4`) the client sends a paid draw only if it holds `floor(cost / item_buy_info(99).rate)` = `floor(2000/2000)` = 1 ticket 99. Otherwise it opens the ticket shop, `ItemBuyPanel` → `5_2933` (`TavernFace.lua:210-237,308-325`, `TavernUI.lua:139-143`). The same holds for the supreme ten-pull (floor(18880/2000) = 9 tickets) and for the mystic card 3000000 with ticket 98 (rate 5888). The gold card sends regardless (`item_entry = 0`, `TavernFace.lua:234-236`), and its cost label shows `gacha_info.item` 100 when owned (`TavernUtil.lua:195-227`). Today the server charges currency in every case, which double-charges a player who bought a ticket.
3. **The tavern tips.** `diamond_gacha == 1` enables the supreme tips. `next == 0` draws "first draw → 2-star hero", and `next = N` draws "N more draws → guaranteed hero" (`TavernFace4.lua:105-123,56-80`). The gold card's tips work the same way with `gold_gacha` and `gold_next` ("→ soul stones", `TavernFace2.lua:56-95`). `diamond_ten_gacha == 0` draws "first ten-pull → 3-star hero" (`TavernFace4.lua:119-123`). The GachaRes copies of these five fields are stored by `TavernUI:synData` (`TavernUI.lua:190-198`).
4. **The post-guide draw pays a 2-star, level-5 hero.** `FIRST_DIAMOND_GACHA_AFTER_NEWGUIDE` = 182000 is a pool of ten heroes: 105000, 203000-209000, 211000 and 301000. Each is `hero_info.star 2, init_level 5`; the memo says "3星", but the table wins. Then `DIAMOND_SINGLE_GACHA_FIRST_INTERVAL` 1 and `DIAMOND_SINGLE_GACHA_NORMAL_INTERVAL` 8 guarantee `DIAMOND_GACHA_HERO_GACHA` 182100. `GOLD_SINGLE_GACHA_NORMAL_INTERVAL` 10 guarantees `GOLD_GACHA_HEROSOULSTONE_GACHA` 181000, and `FIRST_TEN_TIMES_DIAMOND_GACHA` is 183000 (`variables.db`). A prize hero is born at `hero_info.star/init_level` since `de0d03a`.
5. **The levers are gated by function unlock levels, not only by hero level.**
   - The skill tab opens at player level ≥ `function(10050).unlock_level` = **5** (`RoleUI.lua:353`, `FunctionType.lua:1152-1180`).
   - Train opens at `function(10040)` = **8** (`TrainCache.lua:110`).
   - Their guides fire from the level-up panel: `MMPlayerUpgradePanel.lua:172-175` → 11300 (skill) and 11200 (train).
   - A level-3 player at 10022 must therefore replay stages first. 10000 and 10012 are `once = 0`, 6 player xp each, and the climb 3→8 costs Σ `player_xp_for_next_level`(3..7) = **60** xp, i.e. 10 wins. Each level-up refunds `levelup_recovery_energy` 12 energy. The original's new player does the same; ACC-W2-1 includes this grind.
6. **Skill upgrade (`5_2103`).**
   - Single level: `{hero, index}` (`RoleUICtr.lua:220-223`).
   - "Up to the max affordable": `{hero, index, spell_entry = target}` (`RoleUICtr.lua:225-228`, target from `RoleSkillRender.lua:218-220,265-302`).

- **O-W2-9. The hero cap in training.** At `xp_for_level(player level).hero_max_level` the trained hero's xp is held at `need − 1`, which is the client's "full" signal. A potion on a full hero is refused 327945. Only the train module clamps; `level_out`'s banking of xp past the cap is unchanged (Risk 5).

- **O-W2-11. Mystery merchant appearance.**

  - Once it reaches `min_appeared_cost` (120), every spend rolls `appeared_rate` (0.05). At `max_appeared_cost` (600) the merchant appears for sure.
  - At most `MAX_SHOW_STORE_TIMES` (1) per day, only at player level ≥ 16.

- **O-W2-13. Daily-task kinds** are opaque codes. The mapping in task E2 is read from each row's `desc` (quoted there). Kinds tied to arena, guild, chat or nobility (10090, 14030-14070, 53010, kind 30) stay at 0.

Angel-trial enemies are built from the player's own heroes scaled by `angeltrials_level_info` (the only enemy source in the client tables). The details are in tasks B4-B6.

6. **Trial fights and `5_2327`.** If CoinLine/HeroTryLine/AngelTryLine ask for the team with a new fight type, `team.py` must answer it. The support-NPC rule is narrowed to the campaign (`9bf9af6`). Each B4-B6 read-first step checks this; a needed change is a new task, never a silent edit.
7. **Angel trials is the largest unknown** (O-W2-14). Its three commits stand alone, and the system can ship last.
8. **Worktrees without `.stock`** fail every test; the junction step is in Global constraints.
9. **Prize categories** beyond the Wave 1 set still raise in `grant_prizes`. B4-B7 and E2 tests roll the real drop ids (`herotrials_stage_info` drops, `angeltrials_treasure_drop`, daily `drops`), so a raise shows up in tests and not on the emulator.
