# Plan B2: Wave 1 (tutorial unblock, heroes, angels, dailies)

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax. Save this file as `docs/superpowers/plans/2026-11-24-plan-b2-wave1.md`.

**Goal.** Extend the B1 server so that, on a fresh `data/player.db`, the stock new-player guide runs on past the point where it stops today. The equip chain 10180→10210 equips item 10000. Step 10290→10297 summons the goddess 500000 from the ten soul stones that stage 1-2 drops. The chapter-1 star chest behind that mask pays out. The "Equip All" (10310→10313), quality-up (10380) and soul-stone summon (10440→10451) threads work whenever they trigger. The other single-player systems that unlock at level 1 answer as the client expects: sign-in, the 7-day login gift, mail, buying energy and gold, the gold shop, selling items, achievements, sweep and reset. Server-run events that have no data in the client get an honest "closed" answer. Chat's two main-city queries get a valid empty reply, which removes the known `11_2006` Lua error. The client is the spec. Every number below comes from a stock `.db` table or from a Lua line cited next to it.

**Architecture.** It reuses B1's contract (`handlers(registry, settings, conn, cfg) -> {(svc, cmd): fn}`, `fill_required`, `Session.queue`). Phase A is serial and touches shared files: schema, config lookups, notify helpers, `hero.py`, `player.py`, `level.py`. Phase B is parallel: each task owns one NEW module file plus its test file, and none of them touches `server/__main__.py` or `server/modules/login.py`. Phase C is serial: W1 wires Phase B, then E1 adds achievements, which need call sites in already-owned files. Two acceptance runs close it: ACC-1 after Phase A and ACC-2 after Phase C.

**Tech.** `py -3.14`, protobuf 7.36.2, pytest 9, stdlib sqlite3/asyncio, AVD `LOA_API30`. No client (APK) change is needed in this plan.

**Read first.** `docs/superpowers/plans/2026-10-21-plan-b1-tutorial-and-campaign.md` (Global Constraints, settled points 1–13), `docs/protocol.md`, `docs/dev-loop.md` §7 (run 6, pre-launch checklist), `docs/TODO.md`.

## Global constraints (house rules baked in)

- Python is always `py -3.14`. The test command is `py -3.14 -m pytest -q --basetemp=C:/tmp/pytest-loa-<task>`, with a **distinct basetemp per task/worktree** (forward slashes). Never share one basetemp between parallel runs.
- **Never `git push`.** Work on branch `plan-b2-wave1`, cut from `plan-c-english` HEAD `e3c731c`. One local commit per task, or per numbered sub-commit where a task says so. Messages look like `feat(server): ...` and end with the attribution line from the session reminder.
- Parallel tasks run in git worktrees. `.stock/` and `data/` are gitignored, so a worktree has neither and every test that does `Path(".stock")` fails. In each worktree, create a directory junction to the main tree's `.stock` (read-only input) with `cmd //c mklink /J .stock "<main-tree>\.stock"`. Never copy or modify it. Never `git stash` in a worktree (the stash is shared across worktrees).
- `data/player.db` migrations are additive only: `CREATE TABLE IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`, and `ADDED_COLUMNS` in `server/db.py` (checked through `PRAGMA table_info`). Never rebuild a table. Every world kept as `data/player.db.*` must still load.
- Status codes are the client's own `language.db` ids, quoted per handler. Never invent a code. A non-zero body `status` makes `MMMsgDispatcher:onNetMessage` float the language text and **skip** the listener unless that listener registered with `isRecError=true` (`MMMsgDispatcher.lua:107-131`). That is the refusal channel.
- If a Res has **no** `status` field (`HeroEquipAllRes`, `ItemCompositeAllRes`, `BuyXpItemRes`, `ItemBuyRes`, `CheckinExtremeRewardRes`), the native header supplies 0 (TODO "Known client behaviour"). Such a handler cannot refuse. It changes nothing, logs at WARNING, and answers the empty Res.
- Every response and every queued notify goes through `fill_required`.
- Config reads go through `server/config/`. No handler runs SQL against stock `.db` files. `item_info` and `check_award` store TEXT, so cast them.
- Writes: validate first (the whole cost and the whole prize list), then write. This is the same pattern as `item.grant_prizes` (`_checked` before any UPDATE).
- Dates that a human reads (log lines, doc tables) are `dd-mm-yyyy`. Stored values and the `last_login_day` / `daily_day` columns are ISO `YYYY-MM-DD`. Flatpickr and the responsive recipe: **N/A** (this plan has no web UI).
- Do not add an abstraction that has only one caller. Exception: the `db.take_item` / `db.spend` helpers in T1 already have five or more callers in this plan.
- Every `hero` field on the wire is a **hero entry**, not a `heroes.id`. `HeroEquipReq.hero`, `HeroEquipAllReq.hero`, `HeroStarUpReq.hero`, `HeroQualityUpReq.hero` and `HeroCallReq.hero` are all `self.data.entry` (`RoleUICtr.lua:116,153,179,267`; `RoleListCtr.lua:214`).

## Assumptions and open questions

**Settled by reading the client (not open):**

1. **Why the angel step 10290 wedges.** Guide 10293 sends `5_2303 {angel_entry}` (`AngelPreviewCircle.lua:195-197`). Today's zero-stub `SummonAngelRes` carries no `angel`, and `AngelUI:onSummonGod` does `msg.angel.angel_entry = tostring(...)` with no nil check (`AngelUI.lua:80,100`). The VM errors and the guide mask stays up. Run 6 row 12 ("tap did nothing") is this.
2. **Why the equip chain wedges.** It has two causes.
   - (a) `level_out` never pushes a hero notification. `BattleFactoryLevel:toExpInfo` only builds the end-screen display (`BattleFactoryLevel.lua:317-337`), so the client's `ClientHero.level` stays 1 until relaunch. Item 10000 has `item_info.required_level = 2`, so `checkEquipItemState` returns 2 ("level too low") and `RoleUITakeEquipPanel:equipFun` sends nothing (`ClientHero.lua:641-653`, `RoleUITakeEquipPanel.lua:124-139`). Run 6 logged exactly `需求英雄等级:2`.
   - (b) Even with the level fixed, `5_2106`/`5_2164` are zero-stubs. The server changes nothing and pushes no ident-2 notify, so the slot never fills (`RoleUICtr.lua:359-394,462-470`).
3. **A hero needs six item slots on the wire.** `ClientHero:updateData` stores `self.items = d.items` (`ClientHero.lua:153`). `checkIsHadTake` loops `#self.items` (`:525`) and `checkIsCouldProgress` reads `items[1..6]` (`:580-584`). B1 sends `items` empty.
4. **`unit` and `base_unit`.** The hero panel shows `unit − base_unit` as the gear bonus (`RoleAttrPanel.lua:165-166`, `GameAttrManager.lua:250-267`). So `unit` = base stats plus equipped `item_info` stats, and `base_unit` = no gear.
5. **Notification idents and field orders** (`RoleData.lua:21-38,244-357`):
   - 1 player (exists).
   - 2 hero: `ClientHero.HERO_FIELDS`, 60 names (`ClientHero.lua:41-103`), with `refer` = hero entry (`RoleData.lua:487-525`).
   - 3 angel: `AngelManager.ANGEL_FIELDS`, 14 names (`AngelManager.lua:29-44`), with `refer` = angel entry (`RoleData.lua:633-695`).
   - 4 item (exists).
   - 6 task: bit 2 = progress, bit 3 = done, `data[1]` = progress (`RoleData.lua:741-786`).
   - 7 mail: bit 1 = new mail (`RoleData.lua:787-803`).
   - 9 hero base: `ClientHero.BASE_UNIT` (`ClientHero.lua:106-…`, `RoleData.lua:591-627`).
   - All of them use the same byte-indexed flag mask as ident 1. Reuse `notify.flags_for` with a field-order argument.
6. **Angels on login.** `AngelManager:parseAngel` builds the roster from `angel_info` rows with `star == 1 and activation_item_num ~= 0` and overlays `QueryMyselfRes.angels` (`AngelManager.lua:73-108`). **Above player level 10 with zero angels the client forces a logout** (`AngelManager.lua:60-68`), so `angels` must be sent once owned.
7. **Angel shape**, from the real server dump in `BattleUnit.lua:3762-3777`: `spells` = 2 ids (`angel_info.spell0/spell1`), `auras` = 6 entries (`aura0..aura5`, zeros included), level/exp/star. The battle reads the angel only from this `serverInfo` (`BattleUnit.lua:3754-3828`). `team.py`'s angel slot can stay out of `team_base`, because the client builds the angel unit itself.
8. **Angel costs.** Summon costs `angel_info(star 1).activation_item_num` of `activation_item` (`AngelCard.lua:352-353`). For goddess 500000 that is item 500000 ×10, which is exactly the stage 1-2 drop in run 6. Star-up costs the **next** star row's `activation_item_num` (`ClientAngel:upstarDiamondNum`, `ClientAngel.lua:224-231`) plus gold `ANGEL_STAR_UP_COST_{star+1}` (`AngelDiamondPanel.lua:167`).
9. **Hero costs.**
   - Star-up: soul item `hero_info.item` (`break_item` at star ≥ 5), count `hero_growth(hero, star+1).star_up_cost`, gold `HERO_STAR_UP_COST_{star+1}` (`ClientHero.lua:595-624`, `RoleUICtr.lua:91`).
   - Summon from soul stones: Σ `star_up_cost` for `star ≤ hero_info.star` and Σ `HERO_STAR_UP_COST_1..star` (`RoleListCtr.lua:88-113,194-214`).
   - Quality-up needs all six slots filled, then `hero_quality.next`. The client clears its own `items` and sets `quality = next` from the **old** row (`RoleUICtr.lua:159-181,397-424`).
10. **Equip All** equips owned items and also crafts the "directly composable" ones for gold (`RoleEquipPanel.lua:150-165,226-252`, `RoleOneEquipAlert.lua:262-270`).
11. **The success animation needs exactly two events.** Star-up and quality-up count the Res handler plus one `INFO_CHANGE_NTF_HERO` (`RoleUICtr.lua:189-217,320-325`). Send exactly **one** ident-2 notify for that hero, after the Res. The dispatcher already sends the reply before draining the outbox (`server/net/server.py:_on_frame`).
12. **Chat replies.** `ChatRoom:dealWithQueryTalkDataRes` indexes `msg.data[1].talkTimes` with no nil check (`ChatRoom.lua:1161-1166`), so `data` needs one `TalkData`. `QueryHistoryTalkRes` must echo `channel`, and an empty `speaks` is fine (`GameMainChatPanel.lua:87-88,194-197`). **Answer to the brief's "check": yes, a valid empty reply is correct and multiplayer-neutral.**
13. **Server-scheduled activity icons are hidden by default.** They appear only through `5_2046 ControlActivityFunctionNotify` (`GameBtnDataManager.lua:77-100`), which the server never sends. A few always-on buttons (open fund, turntables) are hidden only by `LoginRes.blacklist` (`ClientFunctionBlackList{entry, disabled}`, `LoginSocketData.lua:297-298`, `RoleData.lua:203-227`).
14. **The 7-day login gift.** `player.login_award` bits 1–7 mean claimable and bits 9–15 mean claimed (`RoleData.lua:1699-1713`). Drops come from `variables.LOGIN_AWARD` (`RoleData.lua:1807-1813`). Claiming sends `LoginAwardReq{award_index}` and reads `login_award`/`awards` (`SevenCell.lua:74`, `SevenList.lua:32-43`).
15. **Energy sync.** The client re-asks `5_2013` at `last_recover_time + PLAYER_ENERGY_RECOVER_CYCLE` and treats it as epoch seconds (`GameEnergryTipPanel.lua:45-48,61-63,170-173`). That is `players.energy_at` after `db.refresh_energy`.
16. **VIP 0 cannot buy energy or gold.** `vip_info` row 10000 (energy purchases) and row 10010 (gold purchases) are `vip0 = 0`. A VIP-0 player is refused with 327952 购买次数不足. That is faithful, not a bug.
17. **Duplicate heroes become soul stones.** A duplicate hero from any prize turns into `HERO_DISCOUNT_STAR_{hero_info.star}` × `hero_info.item`, and a duplicate angel into `ANGEL_DISCOUNT_STAR_{star}` × `activation_item` (`variables.db`). Today `item.grant_prizes` inserts a second `heroes` row for the same entry. That is a latent bug, fixed in B3.

**Open: the client says nothing. Each has a default the plan uses, and the owner decides only if he wants otherwise:**

- **O1. Hero `ability` with gear, star and quality.** There is no Lua formula; the client displays the server's number. Default: `npc_info(prototype).ability` (as today). Gear and star do not change it, only quality does, through the prototype. The power shown on the line-up can therefore lag the original.
- **O2. Angel `ability`.** The same gap. Default 0. The real dump shows 1010 at level 5, and no table gives it.
- **O3. Sign-in month.** `checkin` ends at month 202312. Default: use the newest table month with the same calendar month number (November 2026 → 202311), with `total_days` = days of the real month, truncated to the rows present.
- **O4. Gold per "点金" (buy gold).** The variables give `GOLD_BUY_BASE` 50000, `GOLD_BUY_LEVEL_BASE` 320 and `GOLD_BUY_TIMES_RATIO` 0.2, but no formula. Default: `base + level_base × player_level`, times the crit multiplier. Moot at VIP 0.
- **O5. `BuyEnergyRes.energy`/`nextEnergy`.** Default: `energy` = new absolute energy, `nextEnergy` = `ENERGY_BUY_GAIN`.
- **O6. Which function ids go in `LoginRes.blacklist`.** Default: payment-only and server-scheduled features with no client data. These are 10100, 10101, 10102, 10103, 10220, 60010, 70010, 70020, 90010, 90050, 90060, 90090, 90200, 90230, 90250, 90270, 90290, 90310, 90320, 90330, 90340, 90360, 90370, 90380, 90390, 90400. They stay **visible**: 10410 (7-day login), 10600 (premium sign-in tab) and 10610 (7-day activity). **This is the one product choice for the owner**; the default ships unless he says otherwise.
- **O7. Equip All craft depth.** Default: one composite level (`getOneEquipStatus == 2` is "directly composable").
- **O8. Does a body `status` reach Lua?** The B1 code relies on it, but it was never shown on the emulator. ACC-2 step 3 checks it: buying energy at VIP 0 must float 购买次数不足.

## Risks

2. **Quality/star-up animation.** It depends on exactly one hero notify after the Res (settled point 11). A second notify plays the panel twice; zero leaves it hanging. The T7/T8 tests assert the count.
3. **The level > 10 logout** if `angels` is ever empty for a player past level 10 (`AngelManager.lua:60-68`). The T6 test covers the send. A player who skipped the summon would still be kicked; that is stock behaviour.
4. **Ability numbers (O1/O2)** may look lower than the original's. This is cosmetic for the campaign, because the client fights with the `unit` stats.
5. **Prize categories** beyond 1/2/9/11/20/30/40 still raise in `grant_prizes`. Sign-in rows, `check_award` and login drops can contain other categories (13 angel xp, 12 hero xp). B2 and E1 tests must roll the real drop ids of the current month and day 1–7 so a raise shows up in tests, not on the emulator.
6. **Worktrees without `.stock`** fail every test. The junction step is in Global constraints.
7. **Server-restart persistence of `stores` and `events`** depends on JSON columns. Both acceptance runs include the restart pass.
